# agy persistent TUI

The managed adapter uses the persistent native TUI under tmux. Startup requires shared assignment-bound initialization facts in addition to native acknowledgement; hook callbacks or transcript entries alone cannot satisfy that gate.

Before opening the initial user conversation, run `pc workflow agy prepare` in a single-pane tmux window. This launches agy with native status callbacks configured before startup and prints its evidence directory. In that conversation, `PC_AGY_PREPARATION` points to the durable preparation files. If tmux or interactive capabilities are missing, follow the reported correction and reopen through this entry point. Existing conversations must be reopened; callbacks are configured at startup.

Preparation is complete when the callback records a native conversation ID and readable transcript, bound by its launch token to the exact current pane. Preparation creates no Run, reserves no task or checkout, and grants no scheduling authority. Keep the preparation directory available for subsequent current-conversation registration; preparation alone is not registration.

For the initial Run, the caller is the Orchestrator. Run `pc workflow orchestrator start <issue> --type <issue|epic> --provider agy --config <config>` from the prepared conversation. The command registers this exact conversation and pane without launching another agy. Read the returned Attempt's `brief.md`, its immutable context and applicable role/project state. Write the specified `initialization.json` with the exact assignment fields and an additional `conversation` field equal to this native conversation ID. Then run `pc workflow orchestrator initialize <run> --config <config>`. Completion criterion: lifecycle is `running`; registration alone leaves dispatch blocked.

The registered window joins `pc-run-<full-run-id>` with matching `@pc_run_id`. A lone window's session is renamed; otherwise only this window moves. Multi-pane windows and missing/conflicting ownership are rejected. Repeat `start` only from the same prepared conversation to reconcile an interrupted registration, retaining its Attempt. Unknown session ownership remains blocked for inspection. Read the saved Attempt's `takeover.json` and exact pane evidence when reconciling; terminal names cannot establish identity.

Use the managed agy adapter for named persistent roles; follow [Managed Run lifecycle](managed-lifecycle.md) for authority, acceptance, recovery and release.

1. Preflight verifies installed interactive capabilities (`--prompt-interactive`, `--conversation`, `--settings`, `--add-dir`) and tmux. Resolve missing capabilities or configuration failures before dispatch. Startup preserves its pane and Attempt on uncertainty; inspect the recorded tmux address for trust, authentication, configuration or authorization requests. Review those requests explicitly; never confirm them automatically. Completion criterion: exact native conversation identity, live exact pane and native role acknowledgement marker for the current attempt are recorded; the shared role-specific factual initialization gate must also pass.
2. For Run children (epic, worker, landing, pipeline-audit, pipeline-refactor and research-state), the adapter derives the target from the Attempt’s Run. Dispatch requires an existing `pc-run-<full-run-id>` session with matching `@pc_run_id`; children cannot create a session or select another terminal. Each child receives its own `<role>-<short-attempt-id>` window, with pane retention configured before agy starts. View the Run with `tmux attach-session -t pc-run-<full-run-id>`. Completion criterion: the saved `terminal.json` contains the exact pane address and native conversation; peer windows remain independently usable. Project-level Coordinators stay outside this Run workflow.

   For controlled child/replacement startup, initial input uses `--prompt-interactive` with a single delivered brief that includes role initialization instructions. Later messages use verified bracketed paste into the active pane. Native transcript `USER_INPUT` (with `source: USER_EXPLICIT` and `status: DONE`) and status-hook callbacks correlate turns. Submission acknowledgement alone is delivery evidence, not task acceptance. Completion criterion: a uniquely correlated native completed turn (`PLANNER_RESPONSE` with `source: MODEL` and `status: DONE`) is available to the existing receipt workflow while the agent is idle.
3. Before switching to the Run layout, end old agy executions and verify recovery/monitoring will not restart them. Preserve historical records; old terminal layouts are unsupported and cannot be resumed automatically. Reconnect reconciles the saved native transcript and retains the Attempt. A verified process restart uses exact conversation resume (`--conversation <UUID>`) with a new linked attempt and a correlated reconciliation instruction, without replaying its brief. `retryStage` preserves the prior conversation after verified termination; use its explicit `replaceConversation` option only for a verified unavailable-conversation reassignment. Missing conversation or ambiguous native evidence stays pending for investigation or verified reassignment. A replacement Orchestrator requires verified termination of its predecessor. If the owned Run session exists, replacement creates only a new window. If missing, rebuilding requires termination evidence for every historical Run execution, including earlier retries; missing panes alone leave occupancy unknown. Conflicting or unmarked sessions remain blocked and are never claimed or cleaned. Child Retry cannot rebuild a session. Completion criterion: exact session marker and pane identity are verified, the new Attempt is linked to its predecessor, and predecessor output cannot satisfy it.
4. Acceptance uses the common workflow gates. Unused executions receive termination; release requires verified pane absence and the recorded `agy-terminated` marker. Unknown termination retains ownership and blocks checkout reuse. Completion criterion: common cleanup and checkout release have completed.

Native transcript and status-hook data are provider evidence, not the workflow's source of acceptance. Keep them available for reconciliation; missing history leaves results unknown.
